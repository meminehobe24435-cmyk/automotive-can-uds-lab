## 二、ISO-TP（ISO 15765-2）高频问答

### Q1：ISO-TP 是干什么的？为什么需要它？

CAN 一帧只有 8 字节数据。UDS 的很多响应远超过 8 字节 ——
比如读 VIN 是 20 字节，读故障码可能上百字节。ISO-TP 就是把
**长报文切成多个 CAN 帧发出去，在接收端重新拼起来**的传输层协议。

它还要解决：接收方来不来得及收（流控）、丢了帧怎么办（序号+超时）、
多帧之间怎么区分（PCI）。

### Q2：四种帧分别是什么？PCI 字节怎么算？

| 帧型 | PCI 高 4 位 | 格式 | 净荷 |
|---|---|---|---|
| 单帧 SF | `0x0` | `0x0L` + 数据 | L 字节（1–7） |
| 首帧 FF | `0x1` | `0x1H 0xLL` + 数据 | 6 字节 |
| 连续帧 CF | `0x2` | `0x2N` + 数据 | 6 字节 |
| 流控帧 FC | `0x3` | `0x3F BS STmin` | 无 |

- **单帧**：`0x0L` 里的 L 就是净荷长度，1–7。
- **首帧**：后两字节 `H` 和 `LL` 组成 **12 位总长度**，最大 4095。
- **连续帧**：`N` 是序号，从 1 开始，到 15 之后**回绕到 0**。
- **流控帧**：`F` 是流状态（0=CTS 继续，1=WAIT 等待，2=OVFLW 溢出），
  `BS` 是块大小，`STmin` 是最小间隔。

### Q3：为什么单帧最多只能装 7 字节？

因为 CAN 一帧只有 8 字节数据区，PCI 占掉 1 字节，剩 7 字节。
首帧和连续帧要留 2 字节和 1 字节给 PCI 和序号，所以净荷都是 6 字节。

### Q4：BlockSize 是干什么的？

控制**发送方连续发多少帧之后必须停下来等下一个流控帧**。

- `BS = 0`：一次放行，剩下的全发完，不用再等
- `BS = 8`：每发 8 个连续帧就停，等接收方再回一个 FC

为什么需要它？接收方的缓冲区有限。如果发送方一口气灌 100 帧，
接收方处理不过来就会丢帧。BlockSize 是接收方在说"我一次能接这么多"。

本工程在 `test_block_size_forces_multiple_flow_controls` 里
把 BS 设成 4，验证 9 个连续帧会触发至少 3 次流控。

### Q5：STmin 是什么？取值范围？

**Separation Time minimum**，连续帧之间的最小时间间隔。
发送方必须遵守，否则接收方可能来不及处理。

编码方式有点特殊（这是常考的点）：

| 取值 | 含义 |
|---|---|
| `0x00`–`0x7F` | 0–127 **毫秒** |
| `0xF1`–`0xF9` | 100–900 **微秒** |
| 其他 | 保留，按 0 处理 |

注意 **`0x80`–`0xF0` 是保留值**，不能当 128–240 ms 用。
本工程 `decode_stmin()` 对保留值返回 0。

### Q6：连续帧序号为什么只到 15？

因为 PCI 字节只有低 4 位能放序号，4 位最大就是 15（0–15）。
到 15 之后回绕到 0。接收方按"期望序号 = 上一个 + 1，到 15 回 0"
来校验，序号不对就报错。

### Q7：接收方缓冲区不够怎么办？

接收方在流控帧里回 `OVFLW`（`0x32`），发送方必须**立刻中止**发送。
本工程两边都会抛 `IsoTpOverflow`：
接收方发现自己声明的 `max_payload` 小于首帧声明的总长度时回 OVFLW，
发送方在 `_await_flow_control` 里收到 OVFLW 时抛异常。

### Q8：ISO-TP 能不能在没有对端的情况下单向发完一条多帧报文？

**不能。** 这是我在写测试时才真正意识到的：

发送方发出首帧后**必须阻塞等接收方的流控帧**，否则不知道对方能不能收、
一次能收多少。所以：

- 真实场景没问题 —— ECU 和诊断仪是两个独立节点，天然并发
- 但**仿真或测试时必须显式把接收侧放到另一个线程**，
  否则在同一个线程里先 `send()` 再 `recv()` 会直接死锁

本工程 `tests/conftest.py` 里的 `BackgroundReceiver` 就是干这个的。
这个点面试官如果问"你测试怎么组织的"，答这个非常有说服力。

## 三、UDS（ISO 14229）高频问答

### Q9：UDS 是什么？和 ISO-TP 什么关系？

UDS 是**应用层**的诊断服务协议，定义"诊断仪能对 ECU 下什么命令、
ECU 怎么回"。ISO-TP 是它下面的**传输层**。

```
UDS (ISO 14229)     ← 服务语义：读数据、安全访问、刷写
  ↓
ISO-TP (ISO 15765-2) ← 分段重组、流控
  ↓
CAN (ISO 11898)      ← 帧、仲裁、错误检测
```

类比：UDS 是"说什么"，ISO-TP 是"怎么把长句子拆成短信发出去"。

### Q10：肯定响应和否定响应的格式？

- **肯定响应**：`请求SID + 0x40`，后面跟数据。
  例如 `0x22`（读数据）→ `0x62`；`0x10`（会话）→ `0x50`。
- **否定响应**：固定三字节 `7F <请求SID> <NRC>`。
  例如 `7F 22 31` 表示"读数据这个服务，请求超出范围"。

### Q11：常用的 NRC 有哪些？

| NRC | 名称 | 什么时候回 |
|---|---|---|
| `0x11` | serviceNotSupported | 这个服务我没实现 |
| `0x12` | subFunctionNotSupported | 服务实现了，但这个子功能没有 |
| `0x13` | incorrectMessageLength | 请求长度不对 |
| `0x22` | conditionsNotCorrect | 当前条件不允许（如试图写只读数据） |
| `0x24` | requestSequenceError | 顺序错了（如没请求种子就送密钥） |
| `0x31` | requestOutOfRange | 参数超范围（如不存在的 DID） |
| `0x33` | securityAccessDenied | 没解锁安全访问 |
| `0x35` | invalidKey | 密钥错误 |
| `0x36` | exceedNumberOfAttempts | 错误次数超限 |
| `0x37` | requiredTimeDelayNotExpired | 还在锁定延时里 |
| `0x78` | responsePending | 收到了，还在处理 |
| `0x7E` | subFunctionNotSupportedInActiveSession | 子功能在当前会话不可用 |
| `0x7F` | serviceNotSupportedInActiveSession | 服务在当前会话不可用 |

### Q12：会话（Session）是怎么回事？

ECU 有几个"权限级别"，通过 `0x10` 切换：

| 会话 | 值 | 用途 |
|---|---|---|
| default | `0x01` | 上电默认，只能做基础读取 |
| programming | `0x02` | 刷写程序，允许 0x34/0x36/0x37 |
| extended | `0x03` | 扩展诊断，允许写入、例程控制 |
| safetySystem | `0x04` | 安全系统诊断 |

**默认会话下，写类和例程类服务是被拒绝的。**

### Q13：会话检查和安全检查哪个先做？

**先检查会话。** 这是规范惯例，也是我实现时特意守住的一条。

一条请求同时"会话不对"和"没解锁"时，回 `0x7F`（当前会话不支持）
而不是 `0x33`（安全拒绝）。因为"这个服务现在压根不可用"
比"你还没解锁"更准确地描述了现状。

本工程在 `UdsServer._dispatch` 里按这个顺序判断，
`test_write_services_blocked_in_default_session` 守住它。

### Q14：S3 定时器是什么？

**ECU 在非默认会话下，如果 5 秒（S3）内没收到任何诊断请求，
就自动退回默认会话，并清掉安全解锁状态。**

为什么？防止诊断仪断线或崩溃后，ECU 一直停在高权限状态。

诊断仪要保持会话，就周期性发 `0x3E TesterPresent`（通常 2 秒一次）。

本工程的可配置 `s3_timeout` 让测试能把它压到 0.3 秒快速验证。

### Q15：安全访问（0x27）的完整流程？

1. 诊断仪发 `27 01`（请求 level 1 的种子）
2. ECU 回 `67 01 <4字节种子>`
3. 诊断仪用**厂商保密算法**把种子算成密钥
4. 诊断仪发 `27 02 <4字节密钥>`
5. ECU 回 `67 02`（成功）或 `7F 27 35`（密钥错误）

**注意子功能的奇偶规则**：奇数（01/03/05…）请求种子，
偶数（02/04/06…）送密钥。`(sub + 1) // 2` 就是安全等级。

**种子必须是随机的**，否则攻击者可以录一次种子和密钥的对应关系重放。
本工程用"毫秒时间戳 ^ 自增计数 ^ 安全等级"保证同一毫秒内连续请求
也能拿到不同种子。

### Q16：密钥连续输错会怎样？

通常三次错误后 ECU 进入**延时锁定**（几十秒到几分钟）：

- 第 1、2 次错：回 `0x35`（invalidKey）
- 第 3 次错：回 `0x36`（exceedNumberOfAttempts），进入锁定
- 锁定期间任何 `0x27` 请求：回 `0x37`（requiredTimeDelayNotExpired）

本工程的 `test_lockout_after_max_attempts` 和
`test_locked_out_requests_rejected` 分别验证这两个阶段。

### Q17：0x78 响应挂起是什么？算肯定还是否定响应？

ECU 处理耗时较长的服务（比如擦写 Flash）时，如果超过 P2 时间
（默认 50 ms）还没处理完，就先回 `7F <SID> 78` 告诉诊断仪
"收到了，还在处理"。

**格式上它是否定响应帧**（`0x7F` 开头，`0x78` 是 NRC 码），
**但语义上不是失败** —— 诊断仪必须继续等最终响应。

把 `0x78` 当错误处理会导致误判。本工程客户端默认透明处理它，
`test_client_handles_0x78_transparently` 验证这个行为。

### Q18：为什么读 VIN 会走多帧？

VIN 是 17 字节 ASCII。UDS 响应是 `62 F1 90` + 17 字节 = **20 字节**，
超过 ISO-TP 单帧的 7 字节上限，所以必须走多帧。

本工程还有个更极端的用例：一次读 4 个 DID，响应 49 字节。

## 四、DBC 与信号高频问答

### Q19：DBC 文件是干什么的？

描述 CAN 报文和信号定义的文件格式。测试和标定工具靠它
**把原始字节翻译成物理值**。

一行信号定义：
```
SG_ EngineSpeed : 0|16@1+ (0.25,0) [0|16383.75] "rpm" Gateway
                  │  │  │ │   │    │  │          │      └ 接收节点
                  │  │  │ │   │    │  │          └ 单位
                  │  │  │ │   │    │  └ 最大/最小值（物理值）
                  │  │  │ │   │    └ 偏移量
                  │  │  │ │   └ 分辨率
                  │  │  │ └ '+'无符号 / '-'有符号
                  │  │  └ 1=Intel小端 0=Motorola大端
                  │  └ 位长度
                  └ 起始位
```

**物理值 = 原始值 × 分辨率 + 偏移量**

### Q20：怎么算一个信号占哪几个字节？

`EngineSpeed`：起始位 0，长度 16，Intel 小端。
占 bit 0–15，也就是 byte 0 和 byte 1。

物理值 2400 rpm ÷ 0.25 = 9600 = `0x2580`。
小端存储 → `80 25`。所以报文前两字节是 `80 25`。

本工程的 `test_engine_speed_raw_bit_pattern` 就断言这两字节。

### Q21：Intel 和 Motorola 格式有什么区别？

- **Intel（小端）**：低位字节在低地址。起始位就是最低有效位。
- **Motorola（大端）**：高位字节在低地址。起始位是**最高有效位**，
  且信号在字节内的排布方向相反。

**这是最容易出错的地方**，跨字节信号尤其容易搞反。
DBC 里 `@1` 是 Intel，`@0` 是 Motorola。

### Q22：信号有偏移量（offset）有什么用？

让原始值 0 不一定是物理值 0。典型例子是温度：

```
SG_ CoolantTemp : 32|8@1+ (1,-40) [-40|215] "degC"
                          分辨率1 偏移-40
```

原始值 0 → 物理值 -40°C，原始值 255 → 215°C。
这样一个**无符号**字节就能表示 -40 到 215 的温度范围，
比用有符号数省一半编码空间。

### Q23：怎么测信号范围？

按 DBC 定义的 min/max 做边界测试：

1. 正常值：范围内的典型值
2. 边界值：正好等于 min、正好等于 max —— **必须能过**
3. 越界值：min-1、max+1 —— ECU 应该拒绝或做合理性检查
4. 无效值/保留值：比如全 0 或全 F 的哨兵值

本工程 `test_dbc_codec.py::TestRangeValidation` 覆盖了这四类。

## 五、测试设计高频问答

### Q24：你这个项目的测试怎么分层的？

两层：

- **单元级**：PCI 编解码、STmin 换算、信号换算、帧位长计算 ——
  纯函数，不依赖总线，跑得飞快且跨平台
- **集成级**：ISO-TP 收发、UDS 客户端与 ECU 服务端交互 ——
  用 python-can 虚拟总线，每个用例一条独立 channel，互不干扰

另外有一个标记为 `socketcan` 的用例，在真实 vcan 上跑同样的多帧收发，
验证"同一套代码在真实内核 CAN 栈上行为一致"。没有 vcan 时自动跳过。

### Q25：为什么大部分测试用虚拟总线而不是 vcan？

两个原因：

1. **可移植**：虚拟总线在 Windows、macOS、Linux 都能跑，
   不需要 root、不需要装驱动。协作者 clone 下来 `pytest` 就能跑。
2. **隔离**：每个用例一条独立 channel，不会互相串帧。
   vcan 是全局接口，并行跑用例会互相干扰。

真实 vcan 的价值是**验证内核 SocketCAN 路径**，所以留一个用例专门测它。

### Q26：异常路径你怎么测的？

这是测试岗的核心能力，我分了五类：

| 类别 | 例子 | 对应用例 |
|---|---|---|
| 长度错误 | 请求少一个字节 | `test_short_request_nrc_0x13` |
| 参数越界 | 读不存在的 DID | `test_unknown_did_nrc_0x31` |
| 顺序错误 | 没请求种子就送密钥 | `test_key_without_seed_nrc_0x24` |
| 状态不允许 | 默认会话下调写服务 | `test_write_services_blocked_in_default_session` |
| 协议层异常 | 序号错乱、缓冲溢出、超时 | `TestErrorPaths` 全部 |

### Q27：边界测试你测了哪些边界？

- **长度边界**：ISO-TP 的 7 字节（单帧上限）、8 字节（多帧起点）、
  4095（12 位长度上限）。参数化跑 8/9/20/49/100/291/1000 七种长度。
- **序号边界**：连续帧序号回绕点 —— 150 字节需要 25 个连续帧，
  必然跨过 15→0 的回绕。
- **信号边界**：DBC 定义的 min 和 max 必须能通过，
  min-1 和 max+1 必须被拒绝。
- **重试边界**：安全访问第 3 次错误触发锁定，第 1、2 次不触发。

## 六、调试方法论：那个 bug 的故事

**这是整个项目最值钱的一段，一定要会讲。**

### 现象

写完 ISO-TP 后，单帧能通，多帧报错：

```
UdsError: unexpected response SID 0x14 for request 0x22
```

读 VIN 应该回 `0x62` 开头，但收到了 `0x14` 开头的响应。
`0x14` 根本不是任何服务的响应码。

### 第一反应（错的）

我一开始怀疑是并发问题 —— 是不是流控帧和连续帧交错导致的？
改了 FC 的发送逻辑，问题依旧。

### 定位方法

**停止臆测，挂一个嗅探 socket 抓原始帧。** 这是关键的一步：

```bash
python3 scripts/trace_debug.py
```

抓到的帧：

```
t+209.35 ms  0x7E0  03 22 f1 90
t+209.46 ms  0x7E8  01 14 62 f1 90 4c 53 4e
                   ^^ 应该是 10 14
```

一眼就看出来了：**首帧的 PCI 字节是 `0x01`，正确值应该是 `0x10`。**

首帧应该是 `0x10 | 长度高4位`，然后跟长度低字节 `0x14`（20 字节）。
我发成了 `0x01 0x14`，接收端自然把它当成"单帧、长度 1"，
于是净荷变成 `[0x14]` —— `0x14` 就这么来的。

### 根因

我把枚举值当成了 PCI 字节：

```python
class FrameType(IntEnum):
    SINGLE = 0x0
    FIRST = 0x1        # 这是"帧类型序号"，不是 PCI 字节
    CONSECUTIVE = 0x2
    FLOW_CONTROL = 0x3

# 错误写法
ff = bytes([FrameType.FIRST | ((total >> 8) & 0x0F), ...])   # 得到 0x01
```

`FrameType.FIRST` 是 1，PCI 字节应该是 `1 << 4 = 0x10`。

### 为什么单帧没暴露

**因为单帧的 PCI 高四位恰好是 0**。`SINGLE | length` 和
`SINGLE.pci_base | length` 结果一样。所以单帧路径一直是对的，
只有多帧出错。

### 修复

给枚举加了 `pci_base` 属性（`value << 4`），编码统一走它；
同时加了回归测试 `test_pci_base_values` 和
`test_first_frame_pci_is_0x10_plus_length_high_nibble` 把这个坑焊死。

### 这个故事的面试价值

它一次性证明了四件事：

1. **会分层定位** —— 没有在应用层瞎改，而是下沉到帧层看原始数据
2. **有工具手段** —— 知道挂嗅探器，不是靠 print 猜
3. **能找根因** —— 不只修现象，还解释了"为什么单帧没暴露"
4. **会写回归测试** —— 修完加测试防复发

**同类问题的通用方法**：协议分层的问题，永远从**最底层**开始验证。
先确认帧对不对，再看组装对不对，最后看服务逻辑对不对。
顺序反了就是在浪费时间。
